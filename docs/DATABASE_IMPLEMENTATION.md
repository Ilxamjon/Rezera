## 10. Reservation implementation

- Table: `reservations`
- `occupancy_range`: **`tstzrange NOT NULL`**, set via `OccupancyRange::expression()` on model `creating` (computes `[start, end + buffer)`).
- Composite FK: `(resource_id, business_id)` → `resources(id, business_id)`.
- Payment fields on row only (no `payments` table).

---

## 11. Double-booking protection

**Mechanism:** Partial GiST EXCLUDE constraint:

```sql
EXCLUDE USING gist (resource_id WITH =, occupancy_range WITH &&)
WHERE (status IN ('pending', 'confirmed', 'checked_in'))
```

**Blocking statuses:** `pending`, `confirmed`, `checked_in`.

**Non-blocking:** `cancelled`, `rejected`, `expired`, `completed`, `no_show`.

**Back-to-back:** Half-open `[)` ranges — `18:00–21:00` then `21:00–23:00` allowed.

**Concurrent requests:** Second insert receives SQLSTATE **`23P01`**; future booking service should catch `QueryException` and return HTTP **409** `resource_not_available` (already mapped in `ApiExceptionRenderer`).

**Helper:** `App\Support\Database\PostgresMigration::addReservationOccupancyExclusion()`.

**Range builder:** `App\Support\Reservations\OccupancyRange`.

## 16. Known Laravel/PostgreSQL notes

- `tstzrange` and EXCLUDE require raw SQL — not Schema Builder.
- `Reservation::creating` sets `occupancy_range` from timestamps — **not** overlap protection, only denormalization.
- Overlap protection is **only** in PostgreSQL EXCLUDE + future transaction/`FOR UPDATE` in booking service.
